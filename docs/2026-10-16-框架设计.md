## 0. 一分钟费曼版（比喻贯穿全文）

把"RKNN 上跑一个视觉项目"想象成开一家餐厅：

- **rknn-toolkit2** 是锻模厂：把通用的模具（ONNX 模型）锻成这条产线专用的模具（.rknn）。它只开在 x86 Linux 的"工业区"（Python 环境），永远搬不进车间。
- **rknn_model_zoo** 是标准工位样册：每道菜（检测/姿态/OCR…）的上下料手法、检验标准的参考做法（C++ 前后处理例程）。可惜样册是散页的，每道菜的火候数字（8400、类别数、阈值）都潦草写在页边，换菜要重新抄一遍。
- **本框架 = 把散页样册装订成标准工位（插件），再配一张订单（工程包 JSON）**。前厅（PC Studio）接单：选模具、选工位、下单；车间（板端引擎）认单不认人：读订单自动装配流水线开工。**换菜 = 换订单，不改车间。**

## 1. 背景与动机

### 1.1 现状痛点

每做一个新视觉项目，重复同一套手工活：

1. 手写转换脚本（toolkit2 Python：config/load/build/export + accuracy_analysis）
2. 到 model_zoo 找最接近的例程，改硬编码（输入尺寸、类别数、输出张量布局、阈值）
3. 交叉编译、adb push、板上调试
4. 项目收尾后代码即归档，下一个项目又从抄上一个开始

### 1.2 参考项目走读结论（详证见各自走读报告）

| 参考项目 | 值得抄的 | 教训 |
|---|---|---|
| VisionMix（Yoga.*） | `ToolBase` 极简契约（模板方法生命周期 + 能力标记接口）；反射扫 PlugIns 目录发现插件；整方案一个文件换型 | `.prj` 用 BinaryFormatter 二进制——人读不懂、diff 不了、版本脆弱；新框架必须 JSON + 版本号 |
| OpenIVS 一代（WPF） | Manager 分层 + 回调解耦；一键构建脚本全套（bat→py：编译/白名单打包/签名/wheel） | 业务时序写死在 MainLoopManager，换项目改代码；README 教用户改哪几行本身就是债 |
| OpenIVS 二代 | **Sequence Runtime：时序变 JSON 节点图**（ISequenceNode + NodeRegistry + 图执行器）；推理后端按模型后缀自动分派四种接入；模型自带类别/阈值 → 换模型零代码 | ——（这就是本框架要走的路） |
| EASY-EAI-Toolkit-3576 | `api.cmake` 自描述接入（一个 cmake 文件拿全头文件+库+依赖）；`os-release` 双固件自适应选库；`display_pro` DMA-BUF 零拷贝契约 | 算法层闭源 .a；仍是"好用的库"——工程是代码态，换模型/换项目照样改代码重编，无配置化、无一键链路 |

### 1.3 竞品格局（2026-10 调研）

业界 NPU 生态的通用范式是四层：**PC 编译器 → 板端 Runtime → Model Zoo → 应用流水线框架**。逐家对照：

| 厂商 | PC 编译/工具 | 板端 Runtime | Model Zoo | 流水线框架（配置驱动） |
|---|---|---|---|---|
| NVIDIA | TAO / TensorRT | TensorRT/JetPack | TAO Model Zoo | **DeepStream**（GStreamer + config 文件）、Triton |
| Hailo | Dataflow Compiler | HailoRT | hailo_model_zoo | **TAPPAS**（GStreamer 元件 + post-process .so + JSON/YAML 配置）——与本框架定位最完整的对标 |
| 地平线 | OpenExplorer（hb_mapper） | BPU runtime | 算法示例仓库 | **AI Express / XStream**（板端数据流水线框架，配置驱动） |
| AMD/Xilinx | Vitis AI Compiler | VART | Vitis AI Model Zoo | Vitis AI Library（例程级，弱于前三者） |
| **Rockchip** | rknn-toolkit2 | librknnrt | rknn_model_zoo | **【空缺】无官方对应物** |
| 社区/通用 | —— | —— | —— | CodeProject.AI Server（PC 端模块化 AI 服务 + Web UI，Studio 形态参考）；Frigate（垂直 NVR：YAML 配置 + RKNN detector 插件，RK3576/3588 已支持 YOLOv9/YOLOx）——垂直参考，非通用工程框架 |

补充事实：Rockchip 自家 GUI 转换工具（老 RKNN Studio，v1 时代）已停更，社区无替代；Ultralytics 有 `model.export(format='rknn')` 一行导出，但环境仍需自装 toolkit2 且只覆盖 YOLO 系。

**结论：没有任何现成方案组合了"PC Studio（转换+工程包）+ RK 板端配置驱动引擎 + model_zoo 收编插件库"。Rockchip 生态恰好缺第四层。自研成立；架构抄 TAPPAS / AI Express / DeepStream 三家作业。**

## 3. 目标 / 非目标 / 反目标

### 目标
- **一键工程**：Studio 里点一次 → ONNX 转换（toolkit2）→ 生成工程包 → adb 部署到板 → 引擎运行 → Web 页看到结果图与指标。
- **换项目不改代码**：换模型 = 换工程包里的 .rknn + pipeline.json 参数；前后处理全部走插件。
- **收编 model_zoo**：每个模型家族一个插件（pre/post/解码），硬编码收进插件元数据 schema（张量布局、归一化、类别数、解码方式）。
- **可回归**：任何插件/引擎改动，用安全帽金标准逐框比对验收。

### 非目标（明确不做）
- 不做训练/标注（模型来源外部，入口是 ONNX）。
- 不做 Windows 原生转换（toolkit2 约束，转换永远在 x86 Linux/WSL）。
- MVP 不做授权/加密体系（Virbox/Sentinel 式狗可后置；插件接口预留位置）。
- MVP 不依赖 GStreamer（引擎自研轻量流水线；TAPPAS 的 GStreamer 依赖在板端是部署负担）。
- MVP 不做多模型级联/节点图编辑器（M3 再上，走 OpenIVS2 路线）。

### 反目标（出现即失败）
- 板端引擎代码里出现 `if (model_family == "yolov8")` 式散装分支——一切差异必须走插件注册表。
- 工程包格式没有 version 字段、或旧包升级无兼容说明。
- 板上结果与 demo 不一致时靠"改代码凑"而不是查 schema/配置。

## 4. 总体架构

```
┌─ PC Studio（x86 Linux/WSL，Python FastAPI + Web UI）─────────────┐
│ ① 转换向导  ② 工程配置器  ③ 部署监视                            │
│    ↓ 转换任务=独立 Python 子进程（跑 toolkit2 脚本，              │
│      不污染 API 进程内存；任务表 sqlite；产 .rknn+转换报告）      │
└──────────────┬──────────────────────────────────────────────┘
               │ 工程包（目录）：project/
               │   ├ pipeline.json        ← 唯一装配依据
               │   ├ models/*.rknn
               │   ├ plugins.manifest     ← 依赖的插件名+版本清单
               │   └ assets/（类别名、测试图…）
┌──────────────▼──────────────────────────────────────────────┐
│ 板端引擎（C++，native ELF，adb shell 可独立运行）              │
│  装配器：读 pipeline.json → 按注册表实例化 Stage 链            │
│  执行器：MVP 单链同步循环；后续 rknnPool 式线程池/双核亲和      │
└──────────────┬──────────────────────────────────────────────┘
               │
┌─ 插件库（静态注册表起步，接口同 model_zoo 代码形状）──────────┐
│ source: image_dir（MVP）→ rtsp/v4l2（M3）                     │
│ preprocess: letterbox（RGA 硬件加速后置）                     │
│ postprocess: yolov8_det（M0）→ yolov8_pose/cls/ocr（M2）      │
│ sink: image_out（MVP）→ tcp/modbus/http_callback（M3）        │
└──────────────────────────────────────────────────────────────┘
```

## 5. 核心设计

### 5.1 工程包与 pipeline.json（schema v1 草案）

```json
{
  "version": 1,
  "name": "helmet_det_demo",
  "target": { "platform": "rk3576", "runtime": "android-native", "core_mask": "0x3" },
  "models": {
    "det": {
      "family": "yolov8-det",
      "file": "models/helmet_rk3576_int8.rknn",
      "input": { "name": "images", "shape": [1, 3, 640, 640], "layout": "NCHW", "dtype": "int8" }
    }
  },
  "pipeline": [
    { "id": "src",  "plugin": "image_dir",   "params": { "path": "assets/test_images", "loop": true } },
    { "id": "pre",  "plugin": "letterbox",   "params": { "size": 640, "pad_value": 114 } },
    { "id": "inf",  "plugin": "infer",       "model": "det" },
    { "id": "post", "plugin": "yolov8_det",  "params": { "conf_thres": 0.25, "iou_thres": 0.45,
                                                          "classes": ["helmet", "head"],
                                                          "out_layout": "C8" } },
    { "id": "out",  "plugin": "image_out",   "params": { "path": "output", "draw": true, "save_json": true } }
  ]
}
```

要点：
- `version` 必填，引擎拒绝无版本包；schema 升级写迁移说明。
- `out_layout` 这类"换模型就可能变"的事实进配置不进代码（y8p 的 [C/8][S][8] 去 tile 教训）。
- `classes` 等业务语义进包；模型文件的量化方式、校准集记录在转换报告（Studio 管），不进板端包。

### 5.2 板端插件契约（借鉴 VisionMix ToolBase + OpenIVS2 ISequenceNode）

```cpp
class IStage {
public:
  virtual ~IStage() = default;
  virtual int  Init(const nlohmann::json& params, const StageContext& ctx) = 0;
  virtual int  Process(Frame& frame) = 0;   // Frame = 图像缓冲 + 结果 Map
  virtual const StageMeta& Meta() const = 0;
};

#define REGISTER_STAGE(NAME, CLS) /* 编译期静态注册，MVP 不做 dlopen */
```

- `StageMeta` = 插件自描述：输入/输出张量契约、参数 schema（供 Studio 生成配置表单）、能力标记（类比 IToolRun/IMatching：`IsSource`、`IsSink`、`NeedsModel`）。
- Frame 上传多带带的 image buffer 结构起步（不引 OpenCV 全家桶也行，但 MVP 可用 OpenCV 换速度）；RGA/DMA-BUF 零拷贝是 M3 优化项（参考 EASY-EAI display_pro 契约）。
- infer 不是普通插件：`models` 段声明 + `plugin: "infer"` 引用，封装 librknnrt（init/run/outputs），核亲和从 `target.core_mask` 读取。

### 5.3 PC Studio

- **后端**：FastAPI。转换任务起独立 Python 子进程（模板化生成 toolkit2 脚本：config → load_onnx → build(do_quantization) → export_rknn → accuracy_analysis），任务状态进 sqlite；完成后产出 .rknn + 逐层耗时/敏感层报告（PERF_DETAIL/accuracy_analysis 经验复用）。
- **前端**：Vue3 + Vite（builder 可改）。页面：模型库、转换向导（芯片/量化/校准集）、工程配置器（按 StageMeta 动态出表单）、部署监视（adb 通道：push 工程包 → shell 拉起引擎 → 轮询结果图/JSON 指标）。
- **部署通道**：RK3576 走 adb（push + `/data/local/tmp` 落地 + shell 前台跑，日志回传）；Debian 板走 ssh（M2 顺带支持）。

### 5.4 一键链路（用户视角时序）

1. 上传 ONNX → 选 rk3576 / w8a8 / 校准集 → 点"转换"（后台子进程，进度可见）
2. 转换完成后在“新建工程”选模型 → Studio 按 family 拉默认 pipeline 模板 + 插件参数表单 → 微调阈值
3. 点"生成并部署" → 打工程包 → adb push → 拉起引擎
4. 监视页看结果图（画框）与指标（耗时/检出数）→ 可一键回传失败样本

## 7. 约束与风险

| 约束/风险 | 应对 |
|---|---|
| toolkit2 只能 x86 Linux Python（闭源 .so，2.3.2） | 转换固定在 WSL 的 Studio 后端；文档写明这是永久的 |
| RK3576 是 Android 14 | 引擎编译为静态链接 native ELF（NDK r18b 工具链已验证）；V4L2/串口在 Android 受限 → MVP 用 image_dir，RTSP 用 ffmpeg |
| model_zoo 例程硬编码（8400、[C/8][S][8]、归一化） | 全部进 StageMeta/工程包参数；插件单测用 demo 金标准 |
| 工程包兼容性 | version 字段 + 引擎拒绝无版本包 + 迁移脚本 |
| 板端结果与 demo 不一致 | 排查顺序：schema → 输入数据 → 量化报告；禁止改代码凑数（反目标） |
| 将来交付客户的授权 | MVP 不做；IStage/IStudio 接口不暴露文件系统绝对路径，为 Virbox 式授权代理留位置 |

## 10. 审查问答与设计补充（builder check 回填，2026-10-16）

审查员提出 8 个问题，按"已有答案 / 设计决定（标注为我的决定）/ 需用户确认"归类如下。**全部已在文档内解决，无一需要用户在开工前再拍板**；其中"设计决定"各条用户可在审阅时推翻。

1. **金标准三件套与"逐框一致"判据**（已有答案）：三件套已定位（见 §8 路径）。可执行判据：双方跑同一批测试图，输出框列表 JSON，匹配规则 = 类别一致 + 框 IoU ≥ 0.98（等价框中心/宽高 ±2px，沿用双板实测口径）+ 置信度 |Δ| ≤ 0.01；对比脚本是 M0 第一个交付物。M0 插件按 demo 数值细节逐位复刻（letterbox 舍入、归一化位置、NMS 顺序以 demo 为准）；抽象化放 M2 schema 冻结时做，用宽容差回归保护。
2. **adb 宿主归属**（设计决定）：部署通道抽象为可配置 `adb_host`。默认 = WSL 后端 interop 调用 Windows 侧 adb.exe（USB 连板，本机已趟平 Git Bash/WSL 混用 adb 的坑）；备选 = 网络 adb（板子入局域网后两端等价，长期正解）。M0 先走 USB + interop。
3. **librknnrt 版本与可替换性**（设计决定）：工程包随包自带与 toolkit2 2.3.2 配套的 librknnrt.so（取自 rknpu2 runtime 库），不依赖固件系统库；RK3576 固件（驱动 v0.9.8）已验证兼容此组合（y8p_demo 即此配置）。板上包内 .so 优先加载。
4. **转换线的验收标准**（设计决定）：现成模型走逐框回归；Studio 自己转换的产物走双重验收——a) accuracy_analysis 整体余弦相似度 ≥ 0.98 且敏感层清单归档（已知敏感层：score_sum@s8、cls@s8）；b) 板上金标准测试集检测匹配率 ≥ 95%（沿用 i8 vs fp16 对比口径）。量化不可逐位复现，不设逐位标准。
5. **51ms 测量口径**（已有答案）：51.3ms 为 y8p_demo 单模型单链 E2E 单帧耗时（含 inputs_set/推理/outputs_get）。M0 执行器按同口径分段打点（decode/pre/infer/post/draw + E2E），验收 = E2E ≤ 60ms 且 infer 段与 demo 差 ±10% 以内。同步单链预期可达，线程池不提前。
6. **RK3576 核数与 core_mask**（已有答案）：RK3576 = 双核 NPU，合法值 0x1/0x2/0x3（MYRKNN_CORE_MASK 经验在 0x1/0x2 上逐位验证过）。schema 示例 0x3 = 双核，合法。既有实测：多流切分双核反而慢 39%，单模型收益以样板实测为准；M3 验收项"双核并行"改写为"多模型流水收益可测"。
7. **业务资产入库策略与仓库位置**（设计决定）：框架代码建在 `rk/04-rkvision-studio/`（engine/ studio/ docs/ tests/）；业务资产不拷贝——Studio 模型库以路径注册引用现有位置（三件套维持原路径），未来 git 化时业务路径进 .gitignore；保密默认按"不外发"处理。
8. **NDK r18b 是不是硬约束**（设计决定）：M0 沿用 r18b（model_zoo 官方脚本与既有编译链基于它，零切换风险），代码避开 std::filesystem 等 C++17 后期特性；builder 在 M0 第一周做 r26 升级验证（半天级），可行则切换并记录。
