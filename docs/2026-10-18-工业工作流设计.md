# RKVision Studio 工业工作流设计

> 状态：设计稿 v1（2026-10-18）。本文是 Studio「工业工作流」功能域的总设计：任务分类、四类 DL 强项模板、judge 判决 DSL、异常检测冷启动方案、落地路线。
> 实施时本文为唯一依据；实现与本文冲突时，先改本文再动代码。

---

## 1. 背景与定位

### 1.1 工业视觉任务全景（按输出类型分类）

| # | 任务 | 输出 | 最适技术 | Studio 优先级 |
|---|---|---|---|---|
| 1 | 定位/引导 | 坐标+角度 | 传统（模板匹配/几何拟合） | 三期 |
| 2 | 有无/装配校验 | OK/NG | 传统为主，形态复杂时 DL | 二期 |
| 3 | 缺陷检测 | 缺陷框/区域/等级 | DL 检测/分割 | **一期** |
| 4 | 异常检测（冷启动） | 异常图+分数 | 无监督（PatchCore 类） | **一期（差异化主打）** |
| 5 | 物体识别/分类 | 类别+置信度 | DL | 二期 |
| 6 | 计数 | 数量 | 检测+计数逻辑 | 一期（随 judge） |
| 7 | 尺寸测量/公差 | 毫米值 | 传统（标定+亚像素），DL 不介入 | 三期 |
| 8 | 读码/字符 OCR | 码值/字符串 | 专用读码 + DL OCR | 二期 |
| 9 | 分割 | 像素区域 | DL 分割 | 二期 |
| 10 | 安全/行为 | 人+区域事件 | DL 检测+区域逻辑 | **一期** |

业界共识：**传统算法守"几何与规则"（测量/读码/精确定位），DL 吃"外观与语义"（缺陷判别/复杂识别）**。工业落地的标准架构是混合流水线，其物理载体正是"CPU 跑传统算法 + NPU 跑深度学习"的异构 SoC——这就是 RKNPU 的产品位置：**不是替代传统视觉，而是承接工业视觉向"看得懂语义"迁移的增量市场，并把 DL 部分零代码化**。

### 1.2 自由度公式

> Studio 的配置自由度 = UI 配置自由度 × 板端插件库丰富度 × 配置下发通道

通道已有（pipeline.json + 一键部署 + LIVE 回看）；本设计补齐前两项。UI 形态决策：**分段表单卡片，不做节点画布**——工业检测工作流 95% 为线性链，DAG 编辑器是伪需求。

### 1.3 通用骨架（七段式，引擎目标形态）

```
源 → 预处理(光照/仿射) → 定位(ROI,可选) → NPU推理 → 家族解码 → 判决judge → 输出(画面/落盘/PLC)
```

现有插件（M0）：source_image_dir / source_v4l2、preprocess_letterbox、infer_rknn、postprocess_yolov5、sink_image_out、sink_mjpeg。
本设计新增插件见 §8 插件清单。

## 2. judge 判决插件（差异化核心，一期）

工业闭环的最后一米：把"检出框"变成"OK/NG 判决 + 执行动作"。竞品 YOLO demo 全部止步于画框，judge 是 Studio 区别于它们的产品线。

### 2.1 规则 DSL（v1，声明式六规则）

```json
{
  "judge": {
    "rules": [
      { "type": "count",  "class": "scratch", "min": 1, "max": 99, "action": "NG" },
      { "type": "score",  "class": "*",       "thres": 0.45 },
      { "type": "size",   "min_px": 20, "max_px": 5000 },
      { "type": "region", "class": "scratch", "polygon": [[100,100],[500,100],[500,400]], "inside": true },
      { "type": "persist", "frames": 5, "desc": "连续5帧成立才算事件（去抖）" },
      { "type": "regex",  "class": "ocr_text", "pattern": "20[0-9]{2}-[01][0-9]-[0-3][0-9]" }
    ],
    "verdict": "ANY_NG",
    "reset": "new_product"
  }
}
```

**六种规则**：

| type | 参数 | 语义 |
|---|---|---|
| count | class, min, max | 指定类别的检出数量窗口 |
| score | class, thres | 置信度过滤/阈值 |
| size | min_px, max_px | 检出框面积过滤（噪声/大片误检抑制） |
| region | polygon, inside | 多边形区域过滤（框中心点判定） |
| persist | frames | 去抖：连续 N 帧成立才置位 |
| regex | class, pattern | 文本类结果的正则校验（OCR 用） |

- `verdict`：`ANY_NG`（任一规则命中即 NG）或 `ALL_OK`（全部通过才 OK）
- `reset`：`new_product`（产品切换信号/帧间静默）时清空 persist 计数

### 2.2 动作（Actions）

```json
{ "actions": {
    "on_ng":  [ "snapshot:ng/", "plc_write:D100=1", "http:POST http://mes/api/ng" ],
    "on_ok":  [ "plc_write:D100=0" ],
    "always": [ "mjpeg" ]
} }
```

v1 动作集：`snapshot:<目录>`（NG 快照存档）、`plc_write:<寄存器>=<值>`（Modbus TCP，二期先做保持寄存器写）、`http:<method url>`、`mjpeg`（送预览流）。

### 2.3 状态机（工程要点）

产线判决不是单帧函数，是状态机：**在位触发**（光电 IO 或帧差检测"新品到达"）→ 采集 1 帧（或连续 N 帧取中位判决）→ 判决锁存 → 等待下一在位信号。`persist` 去抖与状态锁存都在 judge 插件内部实现，配置里不出现状态机细节。

## 3. 任务模板

每个模板 = 预置 pipeline.json + 默认 judge 规则 + 数据/训练指引。客户选任务类型 → 模板展开为可调表单。

### 3.1 模板 A：缺陷查找（一期）

```json
{
  "version": 1, "name": "defect_scan",
  "target": { "platform": "rk3576", "runtime": "android-native", "core_mask": "auto" },
  "models": { "det": { "family": "yolov8-raw", "file": "models/defect.rknn",
      "input": { "shape": [1,3,640,640], "layout": "NHWC", "dtype": "uint8" } } },
  "pipeline": [
    { "id": "src",  "plugin": "source_v4l2",   "params": { "dev": "/dev/video0", "w": 1280, "h": 720 } },
    { "id": "pre",  "plugin": "preprocess_lightnorm", "params": { "enable": false } },
    { "id": "inf",  "plugin": "infer",          "model": "det" },
    { "id": "post", "plugin": "post_yolov8_raw","params": { "conf": 0.25, "iou": 0.45, "classes": ["scratch","dent","stain"] } },
    { "id": "jdg",  "plugin": "judge",          "params": { "$ref": "本文件 judge 节" } },
    { "id": "out",  "plugin": "sink_mjpeg",     "params": { "port": 8000 } },
    { "id": "arc",  "plugin": "sink_archive",   "params": { "ng_dir": "ng_images", "keep_days": 7 } }
  ]
}
```

要点：`post_yolov8_raw` 是 §8 需新写的家族插件（四形态 DFL 解码，逻辑已在 tools/rknn_sim.py / onnx_infer.py 验证，移植 C++）。

### 3.2 模板 B：安全行为（一期）

与 A 同骨架，差异在 judge 配置：`region`（多边形禁区）+ `persist`（连续 5 帧去抖）+ `class`（"no_helmet"）。源用 RTSP/USB 相机。安全帽模型与数据闭环已验证，是最快出 demo 的模板。

### 3.3 模板 C：异常检测冷启动（一期，差异化主打）

**两阶段产品流程**：

- **注册阶段（PC 向导，Studio 内）**
  1. 从 LIVE 流一键抓 N 张**正常品**图（建议 50~200 张，多光照/位姿）
  2. PC 跑 backbone（ResNet18/MobileNetV3 截断，layer2+layer3 特征）提特征 → coreset 采样（10%）
  3. 生成**模型包**：`backbone.rknn`（NPU 特征提取）+ `memory_bank.bin`（coreset 特征库，二进制）
  4. 阈值校准向导：拉滑块看样图 OK/NG 分界 → 写入 judge 配置
- **运行阶段（板）**

```json
{ "pipeline": [
    { "id": "src",  "plugin": "source_v4l2", "params": { "dev": "/dev/video0" } },
    { "id": "inf",  "plugin": "infer",        "model": "bb" },
    { "id": "ad",   "plugin": "post_anomaly", "params": { "bank": "models/memory_bank.bin",
                                                            "score_thres": 0.5 } },
    { "id": "jdg",  "plugin": "judge",        "params": { "rules": [ { "type": "score", "thres": 0.5 } ] } },
    { "id": "out",  "plugin": "sink_mjpeg",   "params": { "port": 8000 } }
] }
```

实现拆分：NPU 只做特征提取（backbone.rknn）；kNN 距离、多尺度上采样、异常热图在 CPU C++（coreset 数千条向量，毫秒级）。训练/记忆库生成在 PC（Python + 一个开源实现即可，Anomalib 或直接复现 PatchCore 核心 ~300 行）。

差异化价值：**客户不需要缺陷样本、不需要标注**——工业质检最大痛点。MVTec AD 上 PatchCore image-level AUROC 99%+，方法成熟。

### 3.4 模板 D：复杂识别 OCR/分类（二期）

`定位文本区（传统或检测模型）→ 裁图 → OCR 模型(NPU) → regex 判决（日期/批次号规则）→ 输出`。判决 DSL 的 `regex` 规则覆盖"识别结果业务校验"（识别出 2025-13-45 直接 NG）。

## 4. 数据与训练闭环（Studio 角色）

每个模板的数据闭环四步，Studio 提供工具位：

1. **采集**：LIVE 页抓图工具（NG/正常 分目录存档；异常检测只需正常品）
2. **标注/训练**：外部（roboflow/labelimg + ModelScope GPU）——Studio 不做训练，只给指引页
3. **转换与验证**：RKNN LAB 已覆盖（ONNX→.rknn build + 模拟 + 板端 perf）
4. **部署与判决**：WORKFLOW 配置器 + judge

## 5. WORKFLOW 配置器 UI（一期）

新页签 **WORKFLOW / 工作流**（第四页签），分段卡片表单：

```
┌ 源 ────────────┐  [image_dir ▾] 路径…   | [v4l2 ▾] /dev/video0 1280x720
├ 预处理 ─────────┤  尺寸 640 ▾  pad 255   光照归一化 ☐
├ 模型 ───────────┤  [导入 .rknn ▾]  家族 [yolov8-raw ▾]  classes 编缉…
├ 后处理 ─────────┤  conf 0.25  IoU 0.45   （随家族显隐）
├ 判决 judge ─────┤  规则表格（增删行：类型/类别/阈值/区域）  动作勾选
├ 输出 ───────────┤  MJPEG 端口 8000 ☐  NG 存档 ☐ 目录…
└────────────────┘   [生成并部署] [运行] [停止]   → LIVE 页看效果
```

- 生成的 pipeline.json 存入 `projects/<用户命名>/`，进入工程下拉（复用现有 Deployer/ProjectRegistry/运行链）
- 模型库：扫描 `projects/*/models/*.rknn` + 用户导入（复用 RKNN LAB 的导入交互）；家族登记后供后处理下拉

## 6. pipeline.json schema v2 增量

- v1 字段全部保留；新增：
  - `pipeline[].plugin` 新增值：`preprocess_lightnorm` / `post_yolov8_raw` / `post_anomaly` / `judge` / `sink_archive` / `source_rtsp`

  - `models.*.family` 新增值：`yolov8-raw` / `anomaly-patchcore`

## 7. 落地路线

| 阶段 | 内容 | 闭环 |
|---|---|---|
| **M-a 一期** | WORKFLOW 配置器 UI + judge 插件 v1 + `sink_archive` | 缺陷查找 + 安全行为 模板闭环（安全帽模型直接可用） |
| **M-b 一期** | 异常检测：backbone 转 rknn + PC 记忆库生成脚本 + post_anomaly 插件 + 校准向导 | 冷启动质检闭环（差异化主打） |
| **M-c 二期** | Modbus/PLC 插件 + OCR 家族 + regex 判决 + 定位/测量插件评估 | 接真产线（PLC 闭环） |

## 9. 风险与开放问题

- **确定性/节拍**：判决必须逐产品确定性；persist 状态机与丢帧策略要在 judge 内定义清楚
- **PLC 现场协议碎片**：Modbus TCP 先行，Profinet/EtherCAT 不承诺
- **异常检测的组件感知逻辑缺陷**（如"少装一个零件"）PatchCore 不擅长——结合传统规则补充（开放问题，三期评估）
- **post_yolov8_raw 的 C++ 移植**是 M-a 最大工时项，须用 rknn_sim.py 同一批测试图做逐框对拍验收
- 多模型串联（det→crop→cls）schema v2 预留 models 多 key（已支持），pipeline 级联放三期
